# ourprovisions-landing

The public landing page + beta front door for **`ourprovisions.app`**.

Static. No React, no Supabase client library, no Clerk. The entire backend
interaction is a single fire-and-forget `fetch` POST to the Supabase Data API
(anon key) when someone completes the questionnaire; the visitor is then handed
a pre-filled Clerk signup URL on `ourprovisions.velayo.ai`.

**This repo shares nothing with the app** (`ourprovisions`). That is deliberate:
a marketing typo must never be able to fail an app build. The only link between
the two surfaces is an anchor tag.

Source of truth for the design: `ourprovisions/docs/specs/active/SPEC_landing_page_beta.md`
and the approved mockup `ourprovisions/docs/mockups/mockup_landing.html`. Where
prose and mockup disagree, **the mockup wins.**

## Structure — chrome vs. content

Chrome (the reusable system) is kept legibly separate from content (this page's
story) so the next front door in the fleet can lift the pattern without a
framework.

```
index.html              content: markup, copy, images, the questions
assets/
  css/
    chrome.css          reusable: tokens, nav, footer, buttons, form primitive, reveal
    page.css            this page: hero, device demo, thesis, shots, aboard, door
  js/
    door.js             the arrival mechanic (insert → redirect → welcome door) + chrome behaviours
    demo-list.js        decorative: the hero phone's living-list animation
    config.js           GENERATED by build.js from env vars — gitignored
  img/                  sacandaga.jpg + three app screenshots (de-base64'd from the mockup)
build.js                writes assets/js/config.js from SUPABASE_URL / SUPABASE_ANON_KEY
vercel.json             static build config
```

The questionnaire is content: each chip group declares its DB column via
`data-field` (and `data-type="boolean"` where needed), so `door.js` collects
answers generically — add a question in the markup and it is captured for free.

## The arrival mechanic (load-bearing)

On submit, `door.js`:
1. **Fires the `beta_signups` insert (anon key), fire-and-forget.** Never awaited,
   never blocking. If it fails — bad key, CORS, offline — the visitor still
   reaches the door. *Never trap someone at the door because a telemetry row
   hiccuped.*
2. Builds the pre-filled Clerk URL:
   `https://ourprovisions.velayo.ai/sign-up?email_address=<email>&first_name=<first>&last_name=<last>`
   Pre-fill is a courtesy, not a lock — every field stays editable at signup.
3. Shows the welcome door ("there's no App Store download…").

`name` is one column (first + last joined); the split is only carried on the URL
for Clerk. Nothing is ever parsed.

## Environment

| var | purpose |
|---|---|
| `SUPABASE_URL` | e.g. `https://parpauldmbetptkmdwbd.supabase.co` (prod) |
| `SUPABASE_ANON_KEY` | public anon key (already in the app bundle; RLS is the security) |
| `APP_SIGNUP_URL` | optional override; defaults to `https://ourprovisions.velayo.ai/sign-up` |

The anon key is public by design. Security is RLS on `beta_signups`: `anon` may
`INSERT` only, and the **absence** of a `SELECT` policy makes rows unreadable to
visitors — which is what keeps the founder-only `status` / `fit_note` private.

## Local

```
cp .env.example .env.local        # fill in SUPABASE_ANON_KEY
SUPABASE_URL=… SUPABASE_ANON_KEY=… node build.js   # writes assets/js/config.js
npx --yes serve@14 .              # or any static server
```

## Deploy (Vercel)

Separate Vercel project (`ourprovisions-landing`), separate origin from the app.

1. Import the repo → framework **Other**, build command `node build.js`,
   output directory `.` (all encoded in `vercel.json`).
2. Set `SUPABASE_URL` + `SUPABASE_ANON_KEY` in Project → Settings → Environment
   Variables.
3. Deploy to the Vercel-assigned URL first and run the checklist below.
4. **Custom domain later.** When adding `ourprovisions.app`: Cloudflare DNS
   CNAME to Vercel, proxy status **DNS only (grey cloud)** — NOT proxied
   (orange), or Cloudflare-in-front-of-Vercel causes TLS/redirect loops.

## Verification checklist (from the spec)

1. **anon can insert** — submit from the deployed page; a row appears in `beta_signups`.
2. **anon CANNOT read** — with an anon-key client, `select * from beta_signups`
   returns **zero rows** despite rows existing. The critical test — proves
   `fit_note` is safe.
3. **anon cannot update/delete** — attempt via anon; expect denial.
4. **service role reads all** — returns every row incl. `status` / `fit_note`.
5. **CORS** — insert succeeds from `ourprovisions.app` (a different origin than
   the app). Check the browser console, not just the row count.
6. **Pre-fill round-trip** — the door's URL carries `email_address` /
   `first_name` / `last_name`; open it; Clerk's form is pre-filled and editable.
7. **Insert-failure resilience** — break the insert (bad key) and confirm the
   user still reaches the door.
8. **DNS** — resolves, TLS valid, no redirect loop (grey cloud, not orange).

## Images are cached forever

`assets/img/*` is served `Cache-Control: public, max-age=31536000, immutable` (see `vercel.json`). Browsers keep an image for a year and never re-check it, even on refresh. **To change a screenshot, save it under a new file name and update the `<img src>`. Never overwrite an image in place**, or returning visitors keep seeing the old one.
